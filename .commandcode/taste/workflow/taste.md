# Workflow Taste
- Prefers reliable, reusable Python automation for repository housekeeping instead of one-off manual cleanup. Confidence: 0.9
- Prefers conservative, explicitly staged cleanup: before proposing any cleanup, read the most recent handoff to establish the current situation; reconcile any small eligible subset against the full inventory and explicitly account for the rest with blocker categories; before any mutation, provide a read-only dry-run audit with scope, state counts, and blockers; separate discovery/marking from removal; treat work as complete only when merged or pushed with no outstanding work; and require agent/human confirmation before treating dirty or test-looking files as disposable. Confidence: 0.95
- For cleanup workflows, prefers moving recoverable artifacts to the operating system's Recycle Bin instead of permanently deleting them. Confidence: 0.95
- In worktree-cleanup audits, wants ignored output classified by provenance rather than treating all ignored files as unfinished: ordinary .NET/React build and cache residue should be distinguished from source changes and preservation-sensitive SeedSmith/generated deliverables or evidence, which require review. Confidence: 0.9
- For large cleanup inventories, wants extra independent agent audits to supplement conservative automated classification, because a fail-closed tool may report only a small eligible subset and miss the broader worktree population. When an answer covers only the tool's automatic candidates, the user pushes back with terse challenges ("no, what about 100+ worktree?") and expects the FULL population inventory with a total count, partitioned into immediate, strong-but-blocked (e.g. detached), conditional, false-positive, and must-retain groups, plus an explicit acknowledgment when the earlier answer was incomplete. Confidence: 0.9
- Expects the agent to respect concurrent-session/path ownership boundaries: never silently edit files another active session exclusively claims, and prefer marking the goal blocked and asking the owner rather than crossing the boundary. Expects the owner to be able to unblock with a single explicit "this worktree is free" ruling, after which work should resume immediately without further ceremony. Confidence: 0.85
- Expects every change to be backed by running the focused tests plus the repo's static audit/verification gates before deploy, escalating sandbox permissions for local NuGet/.NET build access rather than skipping verification. Confidence: 0.85
- Keeps the current plan of record as a plain-text plan file (e.g. `C:\Users\NeneScarlet\Desktop\plan.txt`) outside the repo and opens sessions by having the agent read it to establish the situation before acting. Also drops additional ad-hoc numbered plain-text handoff/session-log files (e.g. `new 10.txt`) on the Desktop mid-task to hand off the current situation, expecting them to be read and absorbed like the plan file. Confidence: 0.8
- Expects a handoff log to be treated as a claim to be verified against the live repo, not as truth: check `git status`/`git log`/targeted greps and report what is actually committed vs landed-uncommitted vs still missing, cite stale references by file:line, and flag false claims left by earlier bulk/ blind rewrites. Confidence: 0.8
- Expects commit/push/deploy to be a deliberate milestone ("now let's commit and push", "commit and deploy <path>") that rebuilds and deploys every affected artifact (FE, server, injector) rather than assuming an earlier build covers the change. Confidence: 0.8
- For a handover over a dirty working tree, wants every dirty path classified by ownership before any summary: report totals, then partition into owned-by-this-session (safe to commit), owned by another active session (explicit "do NOT touch"), and unfenced/collateral with no session claiming them, each with counts. Expects this done mechanically via a read-only stdlib Python classifier over `git status --porcelain -uall` matched against each active session record's path globs, not by eyeballing status output. Confidence: 0.85
- IMPORTANT — that ownership partition is a safety map, NOT a scope reduction. When taking over an unfinished agent's work, the owner declares the whole dirty tree in scope ("your work is continue the agent work and finish it, 120+ files is in scope") and pushes back on a handover that shrank the job to the files one session record happened to claim. Expect the agent to continue and FINISH the prior agent's plan end-to-end — fix the live defects, write the missing tests, re-point stale citations, run the gates — rather than stopping at a report of what is done vs. still open. "Owned by another active session" is a warning to coordinate, not a licence to leave it. Confidence: 0.9
- After a bulk rename/replacement sweep (old script -> new script, renamed flag, retired citation), expects verification at the invocation level, not just the string level: read the replacement's actual CLI surface and grep every rewritten caller for stale argument/flag syntax. A blind find/replace can leave PowerShell-style flags pointing at an argparse program and silently break every caller while the string-level diff looks clean. Confidence: 0.85
- When an automated classification tool produces a wrong bucket (missed a glob, produced a false negative), expects the agent to say so explicitly in the report and hand-correct the bucket rather than silently emitting a misleading partition. Confidence: 0.8
- Interrogates progress with blunt one-liners ("have you done your work? did we complete the plan") and expects a plan-itemized verdict rather than a narrative: go verify the plan items you never checked before answering, state N of M steps complete, name the exact gap, distinguish which numbers are your own reproduced measurements vs. figures inherited from a prior agent's hand testing, and end by saying what the owner must supply to close the remaining item. Confidence: 0.8
- When reporting on a plan, wants the plan's own risk/assumption items checked one by one against the repo (not just its to-do list), stated as verified/no-fix-needed, and wants deviations from the plan (declined suggestions, work done wider than requested) called out explicitly with the reason. Confidence: 0.8
- Prefers the closing report of a takeover to separate: what was fixed, what was found BEYOND the plan, what was deliberately declined (with the measured reason for refusing), and what still needs an owner decision. Also expects unrequested change that rode along inside an in-scope file to be committed but explicitly flagged as needing its own review, and expects a proof that requires a real environment to be left undone rather than faked. Confidence: 0.8
- That "leave it undone rather than fake it" clause bounds only the genuinely blocked remainder, NOT the whole plan item. A terse "continue work and complete the plan" after a report said an item was blocked is a rejection of stopping there: re-scope the item, measure/deploy/test every part that this machine can actually do (even if the headline number stays unproven), correct the documents the measurement contradicts, commit that, and report only the true remainder. Confidence: 0.8
- Before reporting a goal blocked or asking the owner to unblock, run the full read-only preflight: env vars, real install paths, game/session lock status, running processes mapped to their ports and executable paths, and whether the shared build output tree is actually locked (probe file/directory writability rather than guessing). Then hand the owner a SPECIFIC ask — "kill pid 56816, the other session's server holding dist/" — never a vague "needs your call". A blocking other session's process is never killed unasked. Confidence: 0.8
- When a measurement the agent reproduces contradicts a figure already documented in the repo, sweep every surface that carries that number (docs, spec, the tool's own docstring, test doc-comments explaining a past decision), replace all of them, and have each replacement state its own measurement boundary — which stages were measured, which were blocked, and therefore that a full total is unproven. Do not leave a stale number in one file while fixing it in another, and do not delete the number either: record the partial reading and say what to measure before citing. Confidence: 0.8
- Keeps the repo working tree free of scratch artifacts: probe/measurement scripts and their JSON output go to a scratch dir outside the repo, and `git status --porcelain` is re-checked clean (moving the stray artifact out) before declaring the work done. Confidence: 0.8
- When work is blocked by a resource another session (or the owner) holds — a locked output tree, an occupied port, a running server — do not stop to report the block and do not ask the owner to kill it. Go read the context and hunt for the isolation lever the repo already ships (a private output root, its own port, a helper script exposing `-ServerRoot`/`-OutputRoot`/`-Urls`) and use that instead. The owner's correction arrives terse and corrective — "do not kill, you need to deploy different port, check the context, tool that you have ... for that purpose" — meaning the workaround was sitting in the repo and the block was self-inflicted. Converting a shared tree into a private root is a valid way to measure; finding the lever and proceeding is the expected answer. Confidence: 0.85
- When a real defect surfaces but sits outside the session's fence (and outside the current plan), do not fix it silently and do not leave it only in chat: record its cause, the exact boundary conditions that trigger it (cold vs. warm, empty vs. staged), and the one-call fix in the repo's standing agent instructions (AGENTS.md) beside the facts it contradicts, so the next person reads the cause instead of rediscovering it — then hand the owner the concrete fix and offer to land it as its own commit. Confidence: 0.8
- Treats "merge to mega-merge" as part of the definition of done, asked in the same breath as "have you finished" — the shared integration branch is `features/mega-merge` and the answer must be based on live verification (current branch, upstream, ahead/behind, the commit SHAs present on the branch tip, and the file content itself, e.g. `git show <branch>:<path>`) rather than on what the agent remembers committing. State plainly which of the three states applies: pushed by me, only local, or carried to origin by a concurrent session's push. Note that this is a direct-mode branch: work lands as commits on `features/mega-merge` itself, so there is no PR to open and no separate merge commit — say that instead of hunting for one. Also state, in the same reply, which dirty paths belong to other sessions and will not be touched. Confidence: 0.8
