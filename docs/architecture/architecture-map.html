Where the layers are, and where they overlap

An RPG and empire-building overlay for Plants vs. Zombies Fusion: four processes, eight assemblies, three control loops, three FSMs, a ten-layer actor stack and one battle engine. This page draws all of it, then marks every place a module owns something it should not.

Read it as a schematic, not an essay. A left rule means the node is the single owner of what it holds. A coloured tag is a recorded defect — click it to jump to the register, or click any flagged node to light up what is wrong with it.

STRATUM 01

Processes

Four things run on the player's machine, plus the game itself. The game is a legal third-party install we never patch — we hook it in memory and observe. Nothing here talks to a cloud.

PvZ Fusion The foundation. Owns the board, vanilla damage, spawn/die, the sun bank. We observe it and never rewrite it. IL2CPP · Unity
Injector Harmony patches inside the game process. Hot path. Never awaits the server. src/FusionRpg.Injector
Server SQLite, REST, SignalR. The only place SQL exists. Cold path. src/FusionRpg.Server :5088
Web Browser control room — lawn, roster, stats, progression, storage. web/fusion-rpg-web
Launcher WPF player entry. Installs the loader, picks a port, starts game and server. src/FusionRpg.Launcher
Harmony hooks → event envelope → SignalR / HTTP inbox → SQLite → projections → browser

The rule this stratum exists to protect

Every RPG feature lives in the RPG layer. It is never built by changing what PvZ is. We may observe PvZ's events and contribute signed deltas back; we may not rewrite it, read its current state, or make a feature depend on it representing a concept.

As of 2026-09-16 the write surface is narrower still: no term of the damage equation is written into PvZ at all — attack, plant shield, armor and take-damage multiplier are retired. The lawn transport is a delta over hp, armor1, armor2.

STRATUM 02

Assemblies

A clean DAG, and the one place it matters most: the injector does not reference FusionRpg.Data, which is what keeps SQL out of the hot path. Contracts depends on nothing, which is why shared vocabularies have to be declared there.

Boundary guard

guard-dal.py bans nine SQL-shaped regexes from every .cs outside src/FusionRpg.Data, with an empty allowlist. This is the boundary that holds best in the whole codebase — the injector genuinely cannot reach the database.

STRATUM 03

Control loops and FSMs

Two async systems, deltas not absolutes, record-then-drain. Delay is the designed degradation mode, not a problem to engineer around. Three FSMs exist and are deliberately orthogonal — none of them is a combat FSM.

Hot — Injector Resolves a hit in-process and never awaits the server. Locked: no server round-trip on the hit path. MatchPhase FSM · Idle→Starting→InMatch⇄Paused→Ending
Cold — Server Pushes grants, owns persistence, projects durable state. Never sits between a hit and its apply. UniqueActor FSM · Roster→Deploying→ActiveBound→Retired
Intent — the seam Ephemeral binding of a durable specimen to a live pointer for the length of a match. UniqueBindings · PendingSpawn→Bound→Cleared

Hard ban

No Server FSM may sit between combat.hit and FA* apply. Combat procs never drive UniqueActor transitions. Three orthogonal IDs that are never collapsed: typeId (catalog species), ptr (one Unity object in one match), instanceId (durable specimen GUID).

STRATUM 04

What an actor's numbers are

Ten layers, one fold. Every layer is a source of DerivedModifiers into a single compose in ActorHub — never a stacking tier, because the channel's own DerivedComposeKind already owns how contributions combine. A layer carrying its own stacking rule would be a second composer wearing a new word.

1a · Base species The race. Global, shared, frozen — a player action never rewrites it. species-passive.{speciesId}
1b · Player species What this player's fusion lab made of it. Per (player, species), append-only. player_species
2a · Specimen One unique creature levelling itself. Mutually exclusive with 2b. UniqueCreature allocation
2b · Empire species What an empire learned about fielding a species. Applies to every general actor of it. rpg_actor_progression kind=species
3 · Equipment Bound atoms from equipped items. Works end to end. equip-assign → EquippedBoundAtoms
4 · Passive tree Per player. Projects from owned nodes, gate points and Θ. TreeBoundAtomsCache
5a/5b · Titles Actor and empire title. In build in another program; 5b is the first empire-scope layer. actor-title.* · empire-title.*
6 · Aura / patron Per side per match. Applies from the next match by design. patron.aura
7 · Buff / status Per actor, live, during a match. StatusDerivedMods
Progression input Θ from Dave's level. Species and type levels feed in — or should. RpgProgressionSubsystem

STRATUM 05

The battle engine

A deterministic battle resolver built on the atom effect engine and the FSM. It solves every battle logic. A feature that changes a battle mechanism is an extension of it, built on top — never beside it, never inside a mode.

The law, and the line it draws

A mode is a driver, never an owner. It may own its loop — a turn-ordered delve and a real-time lawn cannot share a scheduler — and it may never own a mechanism.

The engine resolves; it never decides. Deciding is non-deterministic — a player clicks, a policy weighs — so player control and battle AI are a separate system that hands the engine data through IIntentSource. Where to move is AI; whether that move is legal is the engine. Replay works precisely because deciding was never inside.

Mechanisms — one implementation, every mode

  • Damage calculator — OverlayCombatCalculator, two call sites repo-wide
  • Mitigation primitives — pierce, amp, divisive, avoidance band, sigmoid: each declared once
  • Targeting and area — TargetResolver.Resolve, shared by dispatcher, bag, status and actions
  • Resource pools — battle uses LawnActorResourcePools verbatim, by explicit choice
  • Shield — ShieldGate on both apply paths
  • Elements, status, procs, actions, derived stats

Not the engine — separate systems

  • Player control and battle AI — five IIntentSource implementations against one seam: stub policy, siege AI, interactive player, delve raid, replay trace
  • Presentation — VFX, HUD
  • Persistence and encounter selection
  • Loot and reward generation
  • Progression credit — though kill attribution itself is the engine's, because who dealt the fatal blow is a deterministic fact
the modes that drive it
Lawn Real-time, PvZ-driven, injector-side. Cannot be deterministic, so it drives the mechanisms rather than being the resolver. CombatDamageDispatcher → Funnel → FA10
Battle / web match The deterministic round loop: status ticks → initiative → death cleanup → shield upkeep. BattleEngine.Resolve
Delve Party dungeon crawl. Drives the same engine, adds attrition and extraction. DelveBattle → BattleEngine.Resolve
Siege / world assault Base defence and district assault on the world turn. DistrictAssaultResolver → BattleEngine.Resolve
STRATUM 06

Shared vocabularies

Closed sets the code owns. A count here is a contract — assert it, and a change is a reviewed decision. A count of a population (species, items) is a reading and is never asserted.

Atom triggers 13 strings, one declaration since 2026-09-16. AtomTriggers aliases EffectTriggers; a guard fails if a literal returns. Contracts/EffectDtos.cs
Status catalog Host-injected from status-catalog.v{n}.json; kind and payload enums stay closed in C#. StatusCatalog · 24 ids today
Element roster Seven elements plus omni; the ring matrix decides matchup. ElementTable · ElementRingMatrix
Actor resources Six, shared by every faction: hp, stamina, hunger, spirit, qi, poise. A faction difference is a display label, never a branch. DerivedStatChannels
Balance / analytic Closed-form predictors for balance guards and duel prediction. Estimators only — they never decide real damage. Balance/Analytic/*
Web display math The browser re-implements some display formulas in TypeScript. web/fusion-rpg-web
