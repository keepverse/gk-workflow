# Decisions — content-gen

**Generated narrative and seedsmith corpus rules.**

| **Structured story text (2026-09-19)** | Generated story text names entities only through closed ICU tokens (`{lead_*}`, `{c_<slug>}`, `{c_<slug>_epithet}`, `{role_<id>}`) and fills runtime values through closed slots (`{place}`, `{supply}`, `{reward}`, `{cost}`); agreement uses ICU `select` on closed registry tags (`article`, `gender`, `number`); a closed set of semantic tags (`em`, `whisper`, `shout`, `pause`) widens [item/seed-contract.md](item/seed-contract.md) §6's markup ban to meaning-only tags, never HTML or styling. Owner rulings R8–R11, 2026-09-19. Grammar: [narrative-seed/spec-token-grammar.md](narrative-seed/spec-token-grammar.md); registry: `gk-data/packs/fusion/data/seed/narrative/_registry/tokens.v1.json`. | <!-- decisions.md:152 -->
| **Narrative names are tokens (2026-09-19)** | **Story text names entities by token, never by display string.** `gk-data/packs/fusion/data/seed/narrative/_registry/names.en.v1.json` maps each lead token to a display string with closed `article`, `gender` and `number` tags — the Garden Keeper, Hourbloom, the Rotwright (owner rulings R8–R11; the product-vision row above names the same three) — and character seeds supply named characters the same way, unioned at read time and never copied into the authored file. Renaming a lead is one row edit and changes no seed and no brief hash. Seed-side half of `npc-story-events` NS5; loader: [narrative-seed/spec-names-registry.md](narrative-seed/spec-names-registry.md). | <!-- decisions.md:153 -->
| **Generated antagonist content obeys counter-doctrine (2026-09-19)** | **No generated enemy-side character carries a line keyed to its own past encounters with the player, a recruit outcome, a level, a rank or a title**; enemy lines are keyed to the faction's relation band and to world facts only. Owner ruling R13. Enforced as registry rules in `gk-data/packs/fusion/data/seed/narrative/_registry/line-pairs.v1.json` (each rule a test) and validated by `narrative-validators`; the four allegiance rows' bands JOIN `gk-data/packs/fusion/data/seed/dungeon/_registry/disposition.v1.json`, never a copy. Rules: [narrative-seed/spec-character-vocab.md](narrative-seed/spec-character-vocab.md) §6; cross-referenced to [npc-story-events-ideal.md](npc-story-events-ideal.md) §6.12. | <!-- decisions.md:154 -->
| **No hard-coded model in seedsmith (2026-09-19)** | **Every seedsmith model call resolves its model through the one config layer** — `.env` `SEEDSMITH_LLM_MODEL` → `seedsmith.toml` → `LlmCallerConfig`'s default; no adapter, helper or CLI flag carries a model id, and provenance records the model that ran (or the closed sentinels `unrecorded` / `none`). Owner ruling R6. Enforced by `gk-forge/tools/seedsmith/tests/test_no_model_literal.py`, whose five structural shapes (S1–S5) catch the literal a string grep cannot see; the `seedsmith-no-model-literal` invariant row lands with the guard script. Rules: [narrative-seed/spec-model-config-resolve.md](narrative-seed/spec-model-config-resolve.md). | <!-- decisions.md:155 -->
| **The spine is a generated seed kind with a planned frame (2026-09-19)** | **The chapter list, each chapter's piece, its scenes, beat counts and cast are an AUTHORED frame** (`gk-data/packs/fusion/data/seed/narrative/_registry/spine-frame.v1.json`); the model writes the scenes inside it, in one work order, and never changes the frame. Owner rulings R1–R3. Generated scenes load as data through the runtime programs' loader, while the hand-authored Rift prologue keeps story-scene decision S3. Seven chapter slots (the owner's seven-piece answer, 2026-09-19), chained by `after`, with the history fragments chained the same way; a chapter row with no scenes plans no spine cell, so nothing waits on authoring them. Frame: [narrative-seed/spec-arc-shapes.md](narrative-seed/spec-arc-shapes.md) §5. | <!-- decisions.md:157 -->
| **Seedsmith authors in two modes: a delegated agent, or an API (2026-10-02)** | **The authoring step sits behind one seam with exactly two implementations — a DELEGATED sub-agent acting as the authoring LLM, or an API call.** LM Studio is not one of them: it is judged too weak for seed authoring. **In delegated mode the agent MAY hand-edit seed data, and seedsmith is what makes that safe rather than what forbids it**: the agent authors, seedsmith PLANS the work and VALIDATES the result, and `ItemSeedValidator` stays the sole authority on whether a name or a row is legal. This is the one scope in which the standing "generated seed data is never hand-edited" boundary is lifted; in API mode, and for every other generated tree, generate-and-regenerate still holds in full. **Delegated mode runs ONLY on an explicit owner request** — it has no implicit trigger and specifically NO fallback when no API endpoint is configured, because a silent fall into a mode that may edit the corpus is the exact failure this rule exists to prevent. The seam defaults to API mode. Owner ruling, 2026-10-02. Distinct from the model-ID resolution row above, which governs which model id is used and not what performs the authoring. | <!-- decisions.md:156 -->
| **One contract predicate per corpus consumer, never a merged one (2026-10-04)** | **A corpus with more than one consumer gets one sibling predicate per consumer, deliberately not merged.** Consumers of the same corpus do not accept the same entries, so each one's raise set is its own contract: `seed_consumer_violations` (the Python `characteristic_pool/catalog.py` live-seed loader) and `csharp_anchor_consumer_violations` (the C# `AnchorRowReader` / `SpeciesExpander` pair that every C# anchor tool and the `RealAnchorCorpusFixture` family go through) are siblings in `gk-forge/tools/seedsmith/seedsmith/adapters/creatures/anchor/schema.py`, and both are called before any write. **Merging them is wrong twice, which is why this is a rule and not a preference:** a merged predicate starts refusing entries its first consumer loads today — the Python side does not care about `reach` or `targetPreference` at all — and `tests/test_seed_consumer_contract.py` pins each predicate's docstring to its own consumer's exact raise set as its coverage assertion, so widening either one silently destroys the assertion that keeps that consumer honest. Two consumers, two predicates, two tests. Each predicate transcribes guards by **guard name, never by line number**: line citations rotted inside the very edit that introduced them, because moving one import in `catalog.py` shifted every one of them, and a citation that rots on an unrelated edit is not evidence of coverage. | <!-- decisions.md:159 -->
| **Corpus validity is per-consumer, and a fail-fast count is not an extent (2026-10-04)** | **A validity claim is always "valid FOR WHICH CONSUMER"; bare "valid" is an unfinished sentence.** One corpus can pass a consumer completely while a second consumer refuses a quarter of it, because a shipped guard inspects only the fields its own consumer reads — the Python-side predicate certifies entries the C# anchor reader refuses wholesale, so the certificate and the corpus are both real and the sentence joining them is false. **Measure extent with every guard evaluated and no short-circuit across guards**, because a fail-fast validator reports *where it stopped*, never *how much is affected*: `csharp_anchor_consumer_violations` collapses into one pass precisely because `gk-forge/tools/CreatureRecipeReconcileInput/Program.cs` prints the first rejection and returns 1, abandoning the rest of the load — which cost an earlier repair programme four serial rounds, each round discovering only the next guard. Earlier guards shadow later ones for exactly that reason, so a corpus-wide count of one defect class is never the count of entries violating another guard, and that shadowing is what left the true extent of a large corpus defect unknowable for weeks. | <!-- decisions.md:160 -->
| **Regeneration replaces, it does not widen; a provenance change is the owner's call (2026-10-04)** | **A regeneration run may not silently change content provenance, and a count that rises while its provenance changes is a content decision rather than a defect.** The creature corpus re-bucketed every existing entry through the external `family-assignments.json` fallback (mostly `unclassified`) instead of each entry's real on-disk family, because the runner's own startup rebuild of `existing_by_file` called `_family_for(species_id, families)` without `classified_family=entry.get("family")`; separately, a CLI selector that chose `--species` **or** `--pipeline` by if-elif silently ran a full eight-pipeline reclassification of three species and moved a family bucket. In both cases **not one seed file was hand-edited**, so the standing "generated seed data is never hand-edited" rule was satisfied while the content changed underneath it — which is the hole this row closes. **A wider output is not a corrected output.** When a regeneration changes which taxonomy an entry is filed under, that is a choice between taxonomies and it goes to the owner; it is never settled by whichever edit turns a test green, and when the generator cannot express the intended taxonomy at all, fixing the generator is the deliverable. | <!-- decisions.md:161 -->
| **The stale-generated-artifact cascade is a checklist, not an investigation (2026-10-04)** | **Changing a generated corpus invalidates every artifact derived from it, and those artifacts are regenerated in dependency order; establishing that order is part of the task, not a detail found afterwards.** Each derived artifact fails in its own terms and reads as an unrelated defect, so the cascade is discovered one failure at a time rather than planned. Measured: the corpus was re-bucketed from 549 family files into 288, and the first thing it broke was not a test but the documentation — `audit-doc-citations.py --strict` reported 5 HIGH findings for species files that no longer resolve, alongside rows still naming `sunflower-kin.json` and `aerial-flora.json`, all corrected against the live corpus rather than by repointing the path at something that resolves. **Record the derived-artifact order in the same change as the corpus change**, working outward from the corpus, so the next occurrence is a list to walk instead of a set of red tests to explain — and correct a stale derived claim against what the corpus now says, never by making the old path resolve again. | <!-- decisions.md:162 -->
