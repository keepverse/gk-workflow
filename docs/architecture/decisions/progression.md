| Creature progression source and spawn ownership (2026-09-08) | **A gameplay mechanism owns its spawn mechanism and declares that spawn's progression source; a species lookup or `typeId` never chooses it by inference.** A **general creature** associated with the player's empire and lacking a dedicated progression mechanism uses the **empire-wide, per-player, per-species CreatureType progression** fallback. Its species level and automatic allocation apply to every applicable general creature of that species in that empire, including lawn use; the world map later exposes that same scope rather than creating another progression system. A **unique creature** has its own specimen progression, `UniqueCreature` allocation, and unique-specific deploy/acquisition flow (summon, fusion, gacha, capture, or a feature-owned equivalent); it **never** receives the empire species fallback. A **Commander** uses the commander progression/allocation source and likewise never falls through to empire species progression. Different gameplay spawn mechanisms may use different power scales, but must name their source and remain on the one power ladder; no source is silently combined with the empire fallback. **Implemented in the current slice:** `UniqueActorHubCompose` and web-battle composition now resolve Commander plus `UniqueCreature` allocation only; generic lawn projection requires a parsed `EmpireGeneral` claim. The remaining gap is lawn terminal settlement/provenance completeness, tracked in `creature-lawn-deploy` Phase 4. This row supersedes earlier wording that unique creatures receive “species stats plus” their own systems. **✅ Amended 2026-09-12:** Injector Bound Hot that still resolves `commander + CreatureType` for a Bound unique (while sheet Hub uses UniqueCreature) **violates this ownership row** as well as the ActorHub sole Hot compose gate — tracked as wiring gap HF-lawn in [combat-power-number-ideal.md](combat-power-number-ideal.md) / [aptitude-sheet/spec-unique-lawn-wire.md](aptitude-sheet/spec-unique-lawn-wire.md); not closed by Server Hub alone. | <!-- decisions.md:116 -->
| Unique lawn XP receipts (2026-09-08, strengthened) | **A lawn-deployed unique creature earns its own specimen XP from two sources only: an enemy kill with proven lethal attribution to that specimen's currently Bound `instanceId`, and active lawn participation while it remains Bound **or seated as that run's commander** (⚠️ AMENDED 2026-09-18, see the end of this row).** “Proven” means the Injector captured the actual fatal interaction's attacker ptr; a guessed last attacker, type/side match, projectile type, or delayed server inference is never credit. If a hook cannot prove the attacker, it emits no unique-kill candidate. The source is a durable, typed `UniqueSpecimen` claim produced from the authoritative unique row and bound correlation, never inferred from a species/type id, and it never awards empire species XP. Participation is settled only at the specimen's death or the resolved run end from injector-emitted, scaled active-match milliseconds — paused wall time is not rewarded and the Server must not substitute arrival time. Every lifecycle capture has a per-match monotonic occurrence id, preserved on replay; ptr is not a capture identity because IL2CPP may reuse it. Each deployment produces one durable binding session only after `PendingSpawn → Bound`, with one open `(run, correlation)` and `(run, ptr)` mapping. The Data capture transaction atomically appends/locates the canonical fact, validates or closes that binding, inserts or compares its immutable receipt, applies specimen XP, runs the existing level-gain unlock handling, and makes the matching roster transition. A byte-identical receipt replay is a no-op; a key collision with different immutable data is an integrity error; a later redeploy has a distinct correlation-bound session. Kill and participation award values and the participation interval are positive `long` tuning values in `progression.v{n}.json`; the existing specimen XP curve remains separately configurable. There is no hard per-run or lifetime XP ceiling. A level-up is Cold progression: it never awaits on the hit path or directly writes a live Unity stat. It may refresh through the existing safe rehydrate/deploy path; ActorHub remains the sole composer. | Action model (2026-08-22) | **An action is the join row between three programs:** an envelope (*when* — [battle-timeline-map.md](battle-timeline-map.md)), a container of atoms (*what* — [effect-atom-map.md](effect-atom-map.md)), a target rule (*who*), a resource cost, and a usability condition. **Actions are not queued or sequenced on the lawn** — PvZ mode is a stateless observer with no queue and no per-actor turn machine, so the lawn never *schedules* an action. ⚠️ **AMENDED 2026-09-03:** this row originally read *"Actions are a battle-mode concept only… the lawn never schedules an action"*, which contradicted row **Lawn position write (2026-09-02)** below — drafted precisely because *"movement actions need to actually move a plant or zombie on the lawn."* The owner commissioned lawn movement actions on 2026-09-02 (*"let's define some movement action in lawn run… because lawn game don't have really good movement advantage"*). **The reconciliation is narrower than the original wording:** the lawn needs an **activation edge** (an act that raises `OnActivate`), not a scheduler — and `OnActivate` is today an authorable atom trigger that is absent from `EffectDtos.EffectTriggers` and raised nowhere in the injector, so this is a **wiring gap**, not an architectural wall. Scoped in [effect-atom-ideal.md](effect-atom-ideal.md) **Wave 8** §W8.3. The **damage applier and target payload already exist** and are not rebuilt: `DamageApplyPipeline` (single-target by design) and `TargetSpec` / `TargetResolver` (`Single` · `Multi` · `Random` · `All` · `Area`, deterministic ordinal sort, injected `ICombatRng`); the resolver fans one action to N ptrs and the applier applies one delta to one target. What is added is a **typed, closed authoring contract** compiling to that resolver — `TargetSpec`'s string modes and `Dictionary<string,object?>` filters must not reach content, per the atom program's no-dictionaries/no-string-comparison rule. The battle area is a **2-D grid, randomly sized per encounter from the seeded generator** (per-encounter data, never process-wide `CombatPolicy`), **one actor per cell**, distance **Chebyshev** (the metric the shipped `Square` shape already implies). Actions carry `MinRange`/`MaxRange`, `RangeChannel`, `AnchorSource`, and `RequiresLineOfSight`; actors carry a `move.range` derived channel. **The grid is deferred but its parameters are not** — range is not retrofittable, and **with no board every range check must pass**, which is what keeps the basic-attack adoption byte-identical. Move and attack are **two ordinary actions**; the clock decides whether an actor gets both, since readiness is `TimeCostTicks / rate` — no compound action and no Action Points needed. Costs: **validate all, consume all at commit, roll back on any failure**; an interrupted channel has paid, and **cools down**. **Fog of war is deferred** — but `A7`'s AI must read the board through a **view interface** from day one, or fog later is an AI rewrite rather than an implementation swap. | Class system (2026-08-26) | **Free build: the player has no class.** Points go anywhere at one price; classes survive only as **Zomboss AI patterns**. **Twelve aptitudes** are the RPG primary stats and are **sources, not registered channels** — an aptitude is never in `DerivedStatCatalog`, because `share` normalises over the actor's own total and a granted aptitude would silently dilute the other eleven. An actor's allocation ~~is the **sum of four scopes**~~ draws on four scopes (commander → creature type → aspect → unique creature), weighted **commander smallest, unique largest** — a commander allocation replicates across the whole roster, so a dominant one is the worst case. ~~`share` is taken **on the sum**, never per scope.~~ *(struck 2026-09-18 — each scope now resolves alone and the weighting is a tunable; amendment (a) at the end of this row.)* Two read functions, both PS-3: **contests read a `Θ`-free share; magnitudes read `P(Θ)`** — one implementation, owned by `aptitude-tuning`, called by both the resolver and the closed form. **Win rate is the metric** — never fight length, damage dealt or kill time, which penalise survival and cc builds for playing correctly, and never under a clock, which manufactures a pass by penalising long fights. **Two acceptance criteria with different standing**: the **termination invariant** (no pairing of offence-holding builds has `netAttrition ≤ 0` on both sides) is **HARD and blocks the build** — no later layer can repair a pool that refills faster than it drains; the **dominance matrix** (no corner beats every other) is **SOFT and reports with its coverage** — a dominant corner is what the action/passive/skill layer is for, and it is red by design today. **No aptitude cap and no respec cap** (PS-8): respec is available, unlimited, and ~~**priced in a resource fighting also costs**~~ priced as amendment (b) below states. Only the **empire respec** (species scope) may instead be paid with an **earned free empire respec**, one grant per empire level (row *Empire level (2026-09-18)*), and the player chooses which each time. A build preset charges exactly the by-hand price. (a) and (b) do not interact: (a) changes how an allocation is *read*, (b) what *changing* one costs.
