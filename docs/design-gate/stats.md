| **Anything that changes what an actor's numbers ARE — a new stat source, a species/race trait, a title, an aura, a buff, a progression axis, an empire-wide bonus** | [architecture/actor-layer-compose-ideal.md](architecture/actor-layer-compose-ideal.md) · `decisions.md` **Actor layer stack** row | **Added 2026-09-16, after the owner named the failure directly: *"our development is so random, when we extend new feature we never careful check the impact."*** If your feature changes what an actor's numbers are, **it is a layer in the actor layer stack**, and the stack is a **closed vocabulary** — adding to it is a reviewed change, exactly like `ActionCategory` or `AtomKind`. Answer five things in your own spec before building: **which layer** (or is it new); **what scope** (global · per empire · per player · per species · per specimen · per match — scope is what decides who a contribution leaks to, and getting it wrong is how one player's fusion picks nearly defined a species for every player); **what lifetime** (frozen · append-only · per-match · live — frozen and player-mutable cannot share a table, which is why base species and player-modified species are separate layers); **what carrier** (an atom effect container bound at deploy, **or** a registered `IActorStatSubsystem` — two exist, both legitimate, a **third invented per feature is the defect**); and **how it names itself** (GG-49 SourceId provenance, so a contribution can be explained on a sheet and withdrawn). And the rule that is not a question: **contribute `DerivedModifier`s into the one fold, or consume Hub output — never decide the number yourself.** A layer is a *source*, never a stacking tier: the fold is per channel (`DerivedStatDef.Compose`), so "layers sum" never means one layer multiplies another. ⚠️ Two programs were one step from independently inventing an empire-wide stat axis (`world-buff`, `world-map-scope`, and `achievement-title`'s `empire-title.*`) — check this row before adding a fourth | <!-- DESIGN-GATE.md:36 -->
