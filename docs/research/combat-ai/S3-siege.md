# Lane S3 — siege (base-defense) combat decisions, plus the boundary with the world strategic AI

## Summary (≤12 lines)

Siege already runs entirely through the shared `IIntentSource`/`BattleEngine` core — **Built**, not a fork.
`DistrictAssaultResolver` (`IBattleResolver` for `BattleKinds.District`) builds a real 2-D board (Chebyshev,
A10) and calls the ordinary `BattleEngine.Resolve(..., aiTuning: SiegeTuningPolicy.Ai)`; that single argument
opts every actor into `SiegeAiIntentSource` via `BattleRunState.DefaultAiIntentSource`, the same seam
`StubIntentSource`/`InteractiveIntentSource`/`RaidIntentSource` use. Siege adds a real tactical layer on top
(stance + signed aggression tiers, additive XCOM-shaped scoring with a risk term, objective-fallback
pathing, frozen acting order, decision trace) — all live and tested. Siege-specific content is: the
`combatant-kind` discriminator (structures never take initiative), `structure.place` (a dedicated 8th atom
attach point + 17th kind), and construction actions granted via `AdditionalHeldActions`. Two real wiring
gaps remain, both matching the brief's map exactly: `EquippedActionIds` is still never set for a real legion
member (only the hardcoded construction grant is), and cover never reaches the AI's risk term (v1 is
cover-blind by the spec's own admission). The strategic/tactical boundary is clean and single-seamed: one
`WorldCommand` → `IBattleResolver.Resolve` call is the entire handoff; nothing crosses it in the other
direction.

## How decisions are made today in this mode (trigger, who decides, what inputs, what executes)

1. **World-turn cadence (strategic).** `ai-commander`'s `FrontierRulesPolicy` (`gk-core/src/FusionRpg.Core/World/Ai/FrontierRulesPolicy.cs`), a utility scorer over the same fogged `IWorldView` a human plays from (no privileged read), emits one `WorldCommand` per legion per turn — an attack order is a `WorldCommand` indistinguishable in shape from a player's. It is admitted through the same queue, written into the command log, and resolved inside `RpgStore.CommitWorldTurn`'s one transaction (`RpgStore.WorldTurns.cs:527-539`).
2. **The handoff.** `TurnEngine.Step` dispatches a resolved assault command to `IBattleResolver` for `BattleKinds.District` — `DistrictAssaultResolver.Resolve`. This single call is the entire seam between strategic and tactical layers; nothing crosses it in the other direction (the resolver never writes back into `IWorldView`/fog, only into `BattleOutcome`/`WorldSlot`).
3. **Board assembly (siege-specific).** The resolver builds a `DistrictLayout` board, places attacker/defender members (`BuildAnimateSetups`) and any standing structures, grants attacker-side construction actions (`AdditionalHeldActions`), and threads the same `HubInputsFor`/`unlockStateFor` delegates a web match uses so a player-owned specimen composes identically.
4. **Tactical resolution (per round, inside `BattleEngine.Resolve`).** `SiegeAiIntentSource` (an `IIntentSource`) decides, for each actor each round: stance (Hold/Guard/Engage) gates how far it may leave post → signed aggression (-2..+2) sorts candidates into tiers → an additive score (hit-chance 70, objective 50, kill 15, low-HP 10, cannot-counter 10, +round anti-turtle, −risk) picks within the best tier → no target in reach falls back to `TerrainOnlyOccupancy` pathing toward the objective → no path at all holds. Ties break by ordinal actor key. Zero RNG anywhere.
5. **What executes.** The chosen `ActionIntent` is consumed by the same `BattleEngine` round loop every mode shares — `TimelineDispatch`/`BasicAttack.cs`, `EntityStatWriter`/Funnel path unaffected (Core-only, no injector involvement — base-defense-map.md: "No injector work anywhere").

## Per-mode constraints a shared core must respect (timing, determinism/seeds, perf, fog, goldens)

- **Determinism, no RNG at all in the AI** (not even seeded) — every decision is a total order over integers; ties break by ordinal key (`spec-siege-ai.md` R5). Stricter than the lawn's seeded-RNG requirement.
- **Frozen acting order per round** (R4) — recomputed only at round start, never as actors die mid-round.
- **Fog** — `FoggedBattleView`/`FoggedOccupancy` decorate `IBattleView`/`IBoardOccupancy` (siege-fog, module 30); `AggressionOf` is fog-gated like `MaxHpOf` ("a target's own aggression is board information, not self-knowledge"). A shared core's AI reads must all go through the fog-decoratable view, never `BattleRunState` directly.
- **Golden discipline** — every new siege field on `BattleActorSetup`/`BattleActorResult` (`Kind`, `AdditionalHeldActions`, `EquippedActionIds`) is `[JsonIgnore]`/`[JsonIgnore(WhenWritingDefault)]` specifically because these records serialize into `ExpeditionResolverTests.Tier_goldens_are_locked`'s hash — a shared core's new per-actor fields inherit this constraint everywhere, not just in siege.
- **Perf/structural bound**: `ai.maxCandidatesScored` (32) is a named structural cap, not a progression ceiling (comment required, per AGENTS.md's no-hard-ceiling rule).
- **Turn-based, not real-time** — unlike the lawn, siege has genuine discrete rounds; `BattleEngine`'s clock module (`ITimeAdvance`/`NextEventAdvance`) is the shared timing abstraction already in place (battle-engine-ssot.md §2).

## Cross-mode reuse candidates (what this mode already shares / could share)

- **The `IIntentSource` seam itself** — siege is proof the seam already generalizes cleanly to a scored, stance-aware, board-reading tactical AI; a shared combat-AI core for lawn/delve/battle can be built as sibling implementations of the same interface, not a rewrite.
- **`IBattleView`/fog decoration** — the exact pattern (`FoggedBattleView` wrapping the real view) is the template for any other mode wanting partial information without touching the resolver.
- **Additive XCOM-shaped scoring (hit-chance 70 : objective 50 : kill 15 : low-HP 10 : cannot-counter 10 ± round/risk)** — a genuinely reusable scoring shape for any turn-based mode (delve) that wants a legible, tunable target-priority AI; explicitly NOT proposed for the lawn (real-time, trigger-edge cadence per `lawn-combat-ai-ideal.md`).
- **`ai.aggression` derived-stat channel** — already a Hub-composed channel, additively contributed like any other stat; taunt/stealth content authored for ANY mode automatically works for siege's AI for free (and vice versa) since it rides the shared ActorHub compose, not a siege-local field.
- **`BattleTrace.AiDecision`** — a golden-neutral (kept out of `Digest`), opt-in decision-trace mechanism generalizable to any mode's `IIntentSource` for readability/debugging, at zero cost when off.
- **`HubInputsFor`/`unlockStateFor` delegate-injection pattern** — Core stays store-free by declaring a `Func<>` need and letting the Data layer inject it at its own call site; this is the reusable shape for any future mode that needs a live specimen's real stats without crossing the DAL boundary.
- **What is NOT shared and should stay mode-local**: stance (Hold/Guard/Engage) and the objective-fallback pathing are meaningful only where a board and a Core/breach objective exist (siege, maybe delve) — the lawn has neither, per its own ideal doc's explicit "lane-local targeting… deliberately not… utility scoring, lookahead, threat maps" v1 scope.

## Answers to the brief's two direct questions

**Does siege reuse the battle intent core?** Yes — fully. `SiegeAiIntentSource` is one of five `IIntentSource` implementations behind the same seam every mode uses, wired through `BattleRunState.DefaultAiIntentSource` with zero change to `BattleEngine.Resolve`'s signature beyond the pre-existing optional `aiTuning` parameter.

**What is siege-specific?** Structure targets and the `combatant-kind` discriminator (forced-basic-attack, never-initiative path for buildings); the four construction acquisition paths and the `structure.place` atom/attach point; the HoMM3-style cover/shooting model (`siege-cover`, decision 35 — though not yet wired into the AI's own risk term); the stance + signed-aggression two-axis targeting policy (Hold/Guard/Engage is not used by any other mode's AI); and the 2-D board + deterministic A* with the dual-occupancy (solid vs terrain-only) objective-fallback trick. Everything else — the scoring loop's shape, the fog decoration, the resolver contract, the derived-stat channel mechanism — is the shared core already generalized correctly.
