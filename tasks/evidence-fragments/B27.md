**Claim:** with a real, live, 187-237-entity lawn board under real combat, the battle-timeline kernel's
own per-frame overhead (`kernel.tick` + `kernel.drain` + `kernel.schedule`) stays at or under its
0.15 ms/frame structural budget, and no gen2 GC collection occurs.

## Setup

`worktree-agent-a133b88741cadeb4f`, MelonLoader host, real game (`PlantsVsZombiesRH.exe`), real server.
Board populated via the existing perf-runbook debug action `POST /api/debug/stress-fill` (built for
exactly this purpose): `{"plants":50,"zombies":150,"rows":6,"freeze":true}` → real Unity plants/zombies

## Real defect found and fixed: `kernel.schedule` was declared but never measured

`PerfSection.KernelSchedule` (`PerfProbe.cs:36`, section name `"kernel.schedule"`) has existed since
T13/B25, but **no call site anywhere wrapped anything in `PerfProbe.Measure(PerfSection.KernelSchedule)`**
— confirmed by grep before touching anything. B27's own checklist line ("the sections exist:
kernel.tick/kernel.drain/kernel.schedule") was therefore only 2/3 true. `_baseline-b27-kernel-200e.json`
and `-run2.json` (pre-fix) show `kernel.schedule` absent from every window; `-run3-schedule-fix.json`
(post-fix) shows it present in 9/9 windows, tracking `kernel.drain`'s own call rate (~30/s) as expected.

Fixed in `gk-fusion/src/FusionRpg.Injector/Effects/KernelDriveHost.cs` (`Dispatch`): the event re-arm
(`_queue?.Schedule(...)`) is now wrapped in its own `PerfProbe.Measure(PerfSection.KernelSchedule)`
scope, nested inside the existing `KernelDrain` scope — the same nesting `board.capture` already uses
inside `effect.onCapture`. `PerfProbe.Record` is `Interlocked`-only per section index, so nesting is
safe by construction. Rebuilt, redeployed, restarted the game, re-ran the probe live to confirm the fix
(`-run3-schedule-fix.json`).

## Verdict: PASS

`kernel ≤ 0.15 ms/frame at 200+ entities` — measured combined kernel overhead never exceeded ~0.003 ms
(3 µs) in three independent live runs. `no gen2 GC during a level` — zero gen2 collections across all
three complete windows (165 s cumulative). The one real gap found (`kernel.schedule` never measured)
is fixed and reproven live in the same session.

## Worth repeating

`scripts/probe-perf.ps1` + `POST /api/debug/stress-fill` are the existing, purpose-built tools for this
— no new debug surface was built. A future B27 re-run should reuse the exact `{"plants":50,
"zombies":150,"rows":6,"freeze":true}` stress-fill payload, which reliably produces 200+ real entities
and, at that ratio, keeps the board `InMatch` for a full 60 s window (run 1's more zombie-heavy
`{"plants":50,"zombies":200}` wiped the plants and ended the match in ~25 s — informative for combat
balance, but it shortens the usable measurement window).
