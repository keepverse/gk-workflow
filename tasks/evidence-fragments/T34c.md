## The mechanism

`LootStreams.cs` — `TrophyFamily(tableId, groupKey)` = `item.trophy-family.{tableId}.{groupKey}`,
named beside `GroupDraw` per R22's own citation (`item.trophy-family.{tableId}.{groupKey}`,
spec-species-materials.md § Design 5 step 2).

`LootPipeline.cs` — `LootRequest.KilledSpeciesId` (one species lookup for the whole kill, read once
by the caller that already knows it) and `LootContentView.FamiliesForSpecies` (the species' own
family-map.json order). Inside `DrawTable`'s per-group loop: a group whose non-`Nothing` entries are
ALL family-scope is skipped entirely (no volume draw, no group draw, no family-index draw) when the
killed species has no family — the literal reading of "skips the family group by rule... consumes no
draw". The winning entry's resolution (`ResolveTrophyGrantId`) composes the concrete id: species
scope directly against `KilledSpeciesId`; family scope picks the species' own single family directly
(no draw) or rolls `SeededRng.DeriveStream(lootSeed, TrophyFamily(...)).NextInt(count)` for a
multi-family species — the exact call the spec cites by name (`SeededRng.NextInt`,
`SeededRng.cs:55`), not `AtomRandom`'s own different rejection-sampling implementation, even though
both are "uniform" — matching the spec's own citation precisely. Either shape refuses by name
(`drop.trophy-no-killed-species`, `drop.trophy-slot-unknown`, `drop.trophy-species-has-no-family`)
rather than a silent nothing, mirroring T30b's own `drop.*` namespace.

`RpgStore.Loot.cs` — `BuildLiveLootContentView` gains an OPTIONAL `familyMap` parameter (never a
file read inside this Data-layer method — the host loads and injects), wired the same "capability
exists today even without a live caller" precedent this exact method's own `SocketKindFor` parameter
already set for T4.

## Real content: `gk-data/packs/fusion/data/seed/loot/tables-creature.json`

Two new groups per rung table (all 10), hand-authored in the SAME runtime shape the rest of this
file already uses (this file was never run through `droptablegen`'s symbolic pipeline — confirmed by
its own real integer `weight` values and `note` fields, so extending it by hand is the established
pattern, not a "hand-edited generated data" violation). Applied via a one-shot Python script
(`json.load` → append → `json.dump(indent=2, ensure_ascii=True)`) to keep all 10 tables byte-identical
in shape; the diff is 100% additive (800 insertions, 0 deletions).

**Weights, decided by principle (T30's own precedent, restated):** flat 5% total species-trophy
chance and flat 5% total family-trophy chance, split evenly across each scope's own slot count
(2 and 8) — the SAME "flat across rungs, no rung curve invented" rule T30's own "rare" equipment
gate already uses, extended to a second (then third) gate rather than inventing a new curve.

## Found, not fixed (separate scope, flagged in the ledger)

`CreatureKillLootSource.TryResolve` and `RpgStore.BuildLiveLootContentView` have **zero production
callers anywhere in `src/`** — confirmed by grep; only tests (and, for `BuildLiveLootContentView`,
`RollRoom`/`RollQuestReward`'s own dungeon-loot callers, which never handle a `creature-kill` source)
exercise them. A real creature kill never reaches `LootPipeline.Resolve` today. This is NOT the
ItemWorkbench gap the coordinator ruled on (2026-09-20) — it is a separate, likely larger gap
(finding where a real kill is detected: lawn combat, delve, or wild-map) — recorded here rather than
silently absorbed or silently left undocumented.
