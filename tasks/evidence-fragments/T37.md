# T37 — `item-upgrade-tree` a: the executor, armour successor edge

Task: tasks/species-gear-chain-todo.md T37 · spec: docs/architecture/species-gear-chain/spec-item-upgrade-tree.md § Design 1

## The blocker

Design §1 says: *"The executor reads whichever source the base type declares — armour reads the
class ladder's `rung`, everything else reads `successorOf` — one lookup function, two inputs, never
two executors."* This reads as if `rung` alone (cloth=1, leather=2, scale=3, plate=4 per
`classes.v3.json` `classLadders.armour`) is enough to find ONE successor container for a given input.
It is not — the real corpus has no field that narrows a `(role, frame, class, band)` group of several
base types down to the ONE the input becomes.

## Evidence (real corpus, not inferred)

| Check | Command | Result |
|---|---|---|
| Humanoid `footing`, `cloth`/`leather` variant count | `python -c "..."` over `gk-data/packs/fusion/data/seed/items/base-types/**/*.json` | 6 `cloth` base types, 6 `leather` base types, all `(role=footing, frame=humanoid, band=a)` |
| Do `(implicit.family, powerBand)` values disambiguate them 1:1? | same script, printed per-entry | **No** — cloth entries repeat `(atom.evasion, low)` four times (ids `-001,-003,-004,-006`) and `(atom.evasion, trivial)` twice; leather repeats the identical pattern at the same counts. No attribute is unique per entry, and no positional (sorted-id) bijection generalises past this one coincidentally-even case |
| Does `band` track `rung` consistently across roles? | same script, `core-guard`/`humanoid` variant counts per `(class, band)` | `cloth-a=7, cloth-b=1, leather-a=9, leather-b=7, plate-a=12, plate-b=15, scale-b=6` — wildly uneven; a "same band" or "band advances with rung" rule fails immediately outside `footing`'s own 6/6/6/6 coincidence |

## Why this is a hard edge, not a design detail

`gk-data/packs/fusion/data/seed/items/_registry/classes.v3.json` is `frozen: true` with `minCompatibleVersion` semantics
(`stage1aFrozen`'s own note: *"a change to this registry invalidates authored content unless
minCompatibleVersion says otherwise"*), and the spec's own Boundaries section marks **"Any change to
`classes.v*.json`"** as **ask-first**. The spec's own Tunables table already names the successor edge
as *"authored content, not a formula, and a reviewed additive registry change"* — the Design section's
prose undersells this by implying `rung` alone suffices; the Tunables table is the correct, more
careful statement, and the real corpus confirms the Tunables table's reading is the true one.

Two resolutions exist and neither is an implementer's call against a frozen, ask-first registry:

1. **Author real successor edges** (e.g., a per-base-type `successorOf` field on armour too, the SAME
   mechanism T38 already plans for weapon/offhand/jewel — collapsing the "two sources, one executor"
   split Design §1 draws) — a reviewed, additive `classes.v4.json` change.
2. **Rule on a deterministic executor-side pick** (e.g., "the lexicographically-first `containerId` in
   the successor's `(role, frame, class)` group, ignoring `band`") — no registry change, but a real
   design decision the spec does not currently state, and one the card-copy rule (§3: the upgraded
   item is *"a chassis carrying its own identity,"* never presented as the named successor) makes
   defensible, since the specific successor chosen is never shown to the player by name.
