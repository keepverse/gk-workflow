## The mechanism

`ItemWorkbench.Enhance` gains an `assuranceLines` parameter (`IReadOnlyList<AssuranceLine>`, ids +
counts — never a flag, T39's own "free ward" defect was exactly a flag with nothing paid for it).
`TryCoalesceAssuranceLines` is the ONE place a request's lines become debited
`MaterialCostLine`s: coalesced to one per id (duplicates SUM), checked once against
`CostClassMatrix.Allows(op, MaterialClass.Assurance)` (refuses by name on any verb but `Temper` —
today only `Enhance` calls this path), and per-line against the closed assurance id set AND against
which of the three ids Enhance itself reads (`assure`/`protect`; `repair` refuses by name —
`enhance.assurance-line-unrecognized` — it belongs to a future repair attempt, T44).
`EnhanceContext.AssureLoaded`/`WardLoaded` are computed from this SAME coalesced set, and the SAME
set is appended, unconditionally, to the recipe's own resolved cost lines before the ONE
`TrySpendAndApply` call — so there is no second, forgeable input, and "spent on load, whatever the
outcome" (§ Design 4) falls out of the existing unconditional-debit machinery rather than needing
new code. A short assurance stack refuses the whole attempt through the SAME shortfall path any
other short material stack already takes; a replay on the same `correlation_id` returns the recorded
outcome via the pre-existing `Replay` check, before any of this new code even runs.

`CraftAssuranceTuningHub.Tuning.AssureBonusMilli` is read only when `AssureLoaded > 0` — the
overwhelmingly common unassured attempt never depends on the Hub being configured at all, which is
what kept every pre-existing `ItemWorkbenchEndpointsTests`/`ItemWorkbenchSpeciesWiringTests` fixture
green without touching them.

`WorkbenchEndpoints.cs`: `EnhanceRequest` gains `AssuranceLines` (shape-validated at the route — a
malformed entry is a 400, the same posture every other required-field check on this route already
takes); the retired `WardLoaded` flag's own `enhance.ward-flag-retired` refusal is untouched.

## The one-off in the full-suite count

`verify-change.ps1`'s own full Server.Tests run reported 573/574 (one fewer than two immediately
subsequent direct `dotnet test` runs, both 574/574). Investigated rather than ignored: both direct
runs' PER-TEST name+outcome lists are byte-identical (diffed with `sort`+`diff`; the only differences
are per-test millisecond timings, which vary run to run by design). This is consistent with a
transient timeout/scheduling anomaly in a large (~570-test), machine-load-sensitive suite — this
session's own memory already documents "Concurrent sessions, heavy machine load" as a known source
of exactly this kind of one-off variance in large suites, unrelated to any specific change. Not
reproduced; not chased further; recorded here rather than silently observed and dropped.
