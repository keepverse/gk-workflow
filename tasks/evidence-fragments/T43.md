## Which verbs are "T24's decaying verbs" — verified against the spec, not assumed

`spec-craft-risk-ladder.md` §2 names the ladder's own scope directly: *"One ladder serves promotion,
temper, reroll and socket work."* Cross-checked against the real code (`grep`-confirmed): `Enhance`
(Temper), `Promote` (Elevate), `RerollOne`/`RerollAll` (one shared `Reroll` executor), and all three
socket verbs `SocketAdd`/`SocketInsert`/`SocketImbue` (Bore/Socket/Imbue — one shared
`ApplySocketWrite` executor) ALL call `ItemWorkbench.CraftWearFor`. That is seven verbs, not the four
an earlier reading of "the decaying verbs" would have suggested from `SocketImbue` alone — `Bore`/
`Socket` share the identical wear-application codepath as `Imbue` and would have been an inconsistent,
half-finished suppression if left out. `CostClassMatrix.Allows`'s `Assurance` arm now covers
`Temper`/`Elevate`/`RerollOne`/`RerollAll`/`Bore`/`Socket`/`Imbue` — leaving only the three pure-mint
verbs (`Forge`/`Upcycle`/`ForgeGem`, which touch no existing instance) and `Repair` (its own D1
destroy chance, T44's future ask) outside it.

## The mechanism — one effect, one id, two call sites

`CraftWearFor(target, protectLoaded)` gains a `protectLoaded` parameter; when true it returns the
CURRENT durability value unchanged rather than handing it to `CraftRiskPolicy.AfterWear`. Every
caller derives `protectLoaded` from the SAME coalesced assurance lines that get debited (never a
second input) via `TryCoalesceAssuranceLines`, now generalised with a `recognizedIds` parameter so
each verb states which of the three assurance ids it actually reads: Enhance keeps `assure`+`protect`
(T42); Promote/Reroll/the three socket verbs read `protect` only (`assure` raises a success chance
none of them roll — refused by name, `enhance.assurance-line-unrecognized`, if requested). For
Enhance specifically, the SAME `protectLoaded` boolean now feeds BOTH `EnhanceContext.WardLoaded`
(suppresses a peril downgrade, T39/T42) and `CraftWearFor` (suppresses craft wear, T43) — one fact,
two call sites, never a second "craft ward".

`ApplySocketWrite` (shared by all three socket verbs) gained `operation`/`assuranceLines` parameters
and does the coalesce-and-append itself, so `SocketAdd`/`SocketInsert`/`SocketImbue` each just pass
their own `CraftOperation` through.

## No destroy outcome, no new enum member

Confirmed by construction, not by a new test: `CraftWearFor`'s own suppression is a caller-side
branch returning the untouched `current` value — `CraftRiskPolicy.AfterWear`'s own `Math.Max(0, ...)`
floor (never a destroy) is simply never reached when protected. No `CraftOperation`/`MutationOpKind`
member was added; `CostClassMatrix.Allows`'s arm widened, and `TryCoalesceAssuranceLines` gained a
parameter — the closed enums themselves are untouched.
