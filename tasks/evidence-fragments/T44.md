## The formula lives in Core, the wiring in Server

`RepairPolicy.CoverageWithAssurance(baseCoverageMilli, repairLoaded, repairCoverageBonusMilli)` — a
new, pure, `checked` addition (no widening needed: every input is already `long`). `Resolve`'s own
`Math.Clamp(materialCoverageMilli, 0, FullRestoreMilli)` still bounds the result, so R10's "the
destroy chance stands, unconditionally" is true by construction — `CoverageWithAssurance` never
touches `destructionChanceMilli`, a parameter `Resolve` takes independently.

**A real, honestly-recorded finding:** `ItemWorkbench.Repair()`'s own existing call ALREADY hardcodes
`materialCoverageMilli: RepairPolicy.FullRestoreMilli` (already the maximum) — a T23-era placeholder,
not something this task's own scope changes (Files list names `RepairPolicy.cs`/`CostClassMatrix.cs`/
`ItemWorkbench.cs`, not a new "how much material did the player bring" system). This means the
`assurance.repair` bonus, wired correctly, is mechanically a no-op at today's Server-level baseline
(the sum gets clamped straight back to the same max) — the SAME "wire it now, real callers/base-value
changes catch up later" posture T41 already used for this exact key. The formula itself is proven
meaningful at the Core level with an un-maxed baseline (`RepairPolicyTests.cs`'s own new tests); the
Server-level tests instead prove the DEBIT/refusal/replay mechanics, which are real and observable
regardless of the baseline choice.
