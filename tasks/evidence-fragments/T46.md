## What the report computes — and what it deliberately does not claim

`CraftAssuranceHorizonReport.Row` reads `EnhancePolicy.SuccessMilli` (the real per-level odds) and
turns it into `ExpectedAttemptsMilli = 1000×1000/successMilli` — the mean of a geometric distribution.
The doc comment states plainly that this is a **lower bound**: it ignores a failed attempt's own
downgrade risk knocking the target level back down, which can only raise the true expected attempt
count. Modelling the full absorbing-Markov-chain expectation (success / plain failure / downgrade
failure, per level, per band) is a materially bigger computation the spec's own Files list does not
ask for, and inventing a materials-cost figure on top of it would require resolving a recipe's cost at
each level — a `Server`/recipe-registry concern, not something `FusionRpg.Core` alone can do without
reading a file (tunables-ssot: "Core never reads a file"). Choosing the honest, smaller, correctly-
caveated statistic over a larger but overclaimed one follows the same restraint
`CraftingHorizonReport`'s own doc comment already models ("N ≈ 0.19... do not size §4's risk bands as
if this were a progression choice").

The other half — "cost of certainty" — is exact, not an approximation: `assurance.assure` raises
success by a fixed `assureBonusMilli` per charge (T41), so the charges needed to reach 1000‰
(certainty) is `ceil((1000 − successMilli) / assureBonusMilli)`, and dividing that by the REAL corpus's
own per-kill yield (`ExpectedRefIdPerMille`, proven against the T45-authored `drop.web.wave-boss`
entries) gives the expected boss kills to farm it. A zero-yield source prints `long.MaxValue` rather
than throwing on a divide-by-zero — R-G1's own first failure mode ("reachable only in theory"), printed
literally instead of silently produced as a wrong finite number or an unhandled exception.

## `ExpectedRefIdPerMille` — a sibling, not a widened, function

`DropTableDraw.ExpectedEquipmentPerMille` (module 11, load-bearing for `DropVolumeCorpusTests`'s
Θ-pin calibration table) filters on `Kind == Equipment`. Rather than parameterize that tested,
load-bearing function with a filter predicate, `ExpectedRefIdPerMille` is a NEW function with the same
numerator/denominator shape (widen-before-multiply, one divide per group, `DropTableDraw.EffectiveWeight`
for the same ilvl-band gate) filtering on `RefId == x` instead — the two kinds of filter are different
enough call shapes that forking a proven, tested function for a second concern would have been the
SOLID violation, not the two-function shape.

## No test asserts a ratio

Every assertion in `CraftAssuranceHorizonReportTests.cs` is one of: the render is non-empty and
contains its own section headers (a string-shape check, not a numeric reading); `PerSourceYield`
returns exactly `sources × 3` rows (a STRUCTURAL identity between two counts, not a value read from
either); every one of the three closed `AssuranceVerbs` ids appears somewhere (closed-vocabulary
membership, per `validation-ssot.md`'s own carve-out for a vocabulary the code owns); the boss table's
yield for each id is `> 0` (a contract check that T45's wiring is reachable at all — the same "did the
wiring happen" shape T34d-wire's own test used — never a specific number); and the zero-yield case
prints `long.MaxValue` rather than a computed number. No test reads `ExpectedAttemptsMilli`,
`AssureChargesForCertainty`, or `ExpectedBossKillsForCertaintyMilli` against a literal.
