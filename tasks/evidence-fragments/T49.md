## Finding 2 — `craftWearPerAttemptMilli` cannot be re-tuned from THIS report, and is left alone

The report, as built in T46, computes `ExpectedAttemptsMilli` as a **lower bound that explicitly
ignores downgrade backslide and craft wear** (T46's own evidence fragment states this; the doc comment
on `GambleVsAssuranceRow.ExpectedAttemptsMilli` says so). It emits no wear-related number at any level.
This task's own acceptance criterion — *"every changed value cites the report line it was read
from"* — is a hard requirement, and no report line exists that speaks to durability wear. Retuning
`deployment-hierarchy.craftWearPerAttemptMilli` (currently 50‰) in this pass would be citing a number
the report never derived — the same shape of fabrication `docs/DESIGN-GATE.md` and the magic-number
audit exist to refuse. **`deployment-hierarchy.v4.json` is left unpublished at v4; no v5 exists.**
Building the full absorbing-Markov-chain model needed to price wear against downgrade risk honestly is
a materially bigger computation than T46's own Files list asked for (a report "computed from shipped
tuning and the loot corpus", not a new craft-simulation engine) — naming this here rather than either
inventing a number or silently skipping the file.

## Finding 3 — `assureBonusMilli`/`repairCoverageBonusMilli` (craft-assurance) already satisfy R-G1

Unlike wear, the report's `AssureChargesForCertainty`/`ExpectedBossKillsForCertaintyMilli` columns
**are** driven directly by `assureBonusMilli` (currently 50‰), so this IS report-backed ground to judge
it on. Reading the cited lines: at the peril band's start (+15) certainty costs 10 charges / **33.3
boss kills**; at the peril floor (+25 and beyond, where it plateaus) it costs 16 charges / **53.3 boss
kills**. Against gambling's own lower-bound cost (2.0-5.0 expected attempts, ignoring the very downgrade
risk that makes certainty worth buying) this lands inside a bounded, non-degenerate middle: neither
R-G1's failure mode 1 (33-53 kills is a real grind, not "an eternity" — it terminates, and the curve is
monotonic and bounded, never re-opening) nor failure mode 2 (dozens of boss kills is not "cheap enough
to dominate" a mechanic whose unassisted cost is single-digit attempts). **No report-backed reason to
move `assureBonusMilli` or the boss weights either — `craft-assurance.v1.json` stays at v1; no v2
exists.** Re-publishing either file with byte-identical values just to produce a `v{n+1}` artifact
would be churn with no functional content, which the "no in-place edit" rule protects against
precisely so that a REAL change is what a version bump signals.
