## Why "fix the generator and regenerate" cannot be the remedy (step 2 of the instruction)

The rejection happens in the **C# validator's own schema check**, after reading JSON that parses fine, and
it is a function of the field's presence alone (measurement 3). Regenerating changes *who wrote the JSON*,
not *what the C# list allows* — and the generator is **required** to write the field: `topology.stamp_class`
in `seedfile.set_entry` is exactly what T53's own criterion ("every newly generated set entry carries
`setClass`") and the owner's ruling ask for. So a regenerate reproduces the same 910, and "fixing" the
generator to stop emitting `setClass` would violate the criterion this lane is being asked to meet.

**The fork, stated for the ruling:**
- **(a) add the field** — one array element, `KindCatalog.cs:112` →
  `extra: new[] { "themeKey", "theme", "members", "thresholds", "speciesId", "setClass" }` → the validator
  returns to **0 errors** on this corpus (measurement 3 is the proof that this is sufficient and
  necessary). Outside this lane's fence; needs the manager or a lane holding `gk-forge/tools/ItemSeedValidator/**`.
- **(b) drop the field** — the only in-fence way to a green validator — which contradicts T52/T53/T54's
  criteria and the owner's 2026-09-21 ruling. Not taken unasked.
