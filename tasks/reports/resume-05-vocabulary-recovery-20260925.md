## Outcome

The FamilyExpand refusal/provenance sidecar is now readable by the existing closed-kind `AtomSeedFile` consumers that enumerate every `gk-data/packs/fusion/data/seed/atoms/**/*.json` file without first applying `SeedScanner`'s underscore exclusion.

The manifest keeps its refusal and provenance model intact:

- root `kind` is the existing closed seed kind `affix`;
- root `entries` is deliberately empty, so the sidecar imports zero runtime content;
- the generator-specific `inputs`, `outputs`, and `refusals` arrays remain unchanged in meaning and are all retained;
- `FamilyExpandManifest.Parse` requires the compatibility kind and rejects a non-empty `entries` array, preventing refusal rows from being reclassified as importable affix content;
- the input/output hashes still cover the provenance and generated-output descriptors, while `FamilyExpandGen --check` compares the complete canonical manifest.

No Core production code, Core test, Delve file, CI file, unrelated fixture, session record, or pipeline file was edited. No commit, push, branch, or merge was performed.

## Root cause and repair

`AtomSeedFile.ReadInto` reads the root `kind` before it reads any entries. The draft manifest had `schemaVersion`, generator metadata, `inputs`, `outputs`, and `refusals`, but no root `kind` and no `entries` array. Tests such as `TraitMigrationParityTests` and `EventDeckGoldensTests` intentionally collect the real atom corpus directly, so `Str(root, "kind")` became `""` and the reader returned `AtomRejectionReason.UnknownKind` before reaching the custom manifest arrays.

The repair is in `gk-forge/tools/FamilyExpandGen/FamilyExpandManifest.cs`, not in Core and not in the generated JSON by hand:

1. `ToCanonicalJson` emits `kind: "affix"` and `entries: []` as a compatibility envelope.
2. `Parse` validates both fields.
3. The real manifest payload remains in the existing custom arrays.
4. A regression test serializes a manifest with provenance and a refusal, feeds it through the real `AtomSeedFile.Collect`, and proves zero errors and zero imported rows.

`affix` is the compatibility discriminator because FamilyExpand expands authored affix-family definitions and `affix` is already in `AtomSeedFile`'s closed vocabulary. It is not a claim that the manifest contains an affix row; the empty `entries` array is the load-bearing part.
